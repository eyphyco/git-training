# sear-and-build（Git Training 版）

目的は「レビューできる実装ができるまでの時間」を短くすること。ユーザーが読んで考える時間がいちばんの律速なので、質問は最小限にし、ユーザーが一覧を読んでいる間に実装を進める。

> 発想の元: magicant/settings の同名スキル。本ファイルはこのプロジェクト向けに日本語で書き直したもの。

## 1. 先に調べる

- 質問する前に、設計書（docs/design.md）・CLAUDE.md・既存コード・テストを読み終えておく。質問中にユーザーを待たせない
- 決めるべきことを全部書き出し、答えをもらうたびに見直す

決めることは、次の順で分類する。

**どこから答えが出るか**
- **導出できる**：設計書、既存コードの慣習、Git の実際の挙動（ゴールデンテストで確かめられる）から決まる → 質問しない
- **意図による**：ユーザーの優先順位・今後の予定・好みで決まる → 次へ
- どちらが正しいか自信がなければ「意図による」として扱う

**覆したら何が変わるか**（意図によるものだけ）
- **形が変わる**：型・データ構造（RepoState / World / レッスン JSON の形式）・モジュールの境界・作る範囲 → 質問する
- **中身だけ変わる**：文言・解説文・テストケースの選び方・コミットの分け方 → 質問しない
- 迷ったら質問する。ユーザーに「それは中身なので聞かなくていい」と言われたら、以後の同種の判断に適用する

コミットの仕方などの進め方は設計判断ではない。CLAUDE.md の定常ルールに従う。

## 2. 形が変わる・意図による判断だけを質問する

- 1問ずつ聞き、毎回「残りの論点と、あと何問くらいか」を先に伝える
- 導出できる判断を質問に混ぜない（それは手順3の一覧に入れる）
- 具体的な選択肢と推奨案を出し、推奨の理由とコストを1〜2行で書く
- 小さな事実はその場に引用し、大きな設計はリンクで示す

## 3. 決めたことの一覧を出して、すぐ実装する

- 質問が残っていなければ、自分で決めたことを1つの一覧にまとめて出し、承認を待たずに実装を始める
- 各項目には (1) 決定内容 (2) 分類（導出 / 中身）(3) 最も有力な別案を1文、を必ず書く
- 異論が出そうな順に並べる（実装の順番は依存関係で決める）
- 実装中に異論が出たら、その項目に関係する部分だけをやり直す
- push・PR 作成・公開など外部に出る操作は、この一覧とは別にユーザーに確認する

## 4. 差分ではなく対応表を返す

- 実装後、「決定事項 → 実装場所（ファイル・関数名・行）」の対応表を出す
- 行番号は記憶から書かない。最後の編集の後に `git diff` か grep で確かめた値を使う
- 関数名・見出しなど、ずれない目印を先に書き、行番号は補助として添える
- テスト結果（Vitest・ゴールデンテスト・レッスン自動実行・E2E）は事実どおりに報告する
